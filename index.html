Synchronization

เมื่อหลาย process หรือ thread ทำงานพร้อมกันและใช้ข้อมูลร่วมกัน ผลลัพธ์อาจผิดได้ขึ้นอยู่กับว่าใครทำคำสั่งก่อนหลัง บทนี้อธิบายว่าปัญหาเกิดจากอะไร และเครื่องมือที่ใช้บังคับให้เข้าใช้ข้อมูลร่วมทีละคน ได้แก่ Peterson's solution, mutex lock และ semaphore

6.1 Background

Producer–Consumer กับตัวแปร count

นึกถึงร้านขนมที่มีชั้นวางจำกัด (bounded buffer) คนทำขนม (producer) วางขนมบนชั้น คนขาย (consumer) หยิบออกไป เราใช้ตัวแปร count นับว่าบนชั้นมีขนมกี่ชิ้น ผู้ผลิตทำ count++ ผู้บริโภคทำ count--

แยกกันรันทีละฝั่งก็ถูกต้อง แต่ถ้ารันพร้อมกัน ค่า count อาจผิดได้ ถ้าเริ่มที่ 5 แล้วทั้งสองฝั่งทำคนละครั้ง คำตอบที่ถูกคือ 5 แต่ค่าที่ได้จริงอาจเป็น 4, 5 หรือ 6

producer
while (true) {
  /* produce an item in next_produced */
  while (count == BUFFER_SIZE)
    ; /* do nothing */
  buffer[in] = next_produced;
  in = (in + 1) % BUFFER_SIZE;
  count++;
}
consumer
while (true) {
  while (count == 0)
    ; /* do nothing */
  next_consumed = buffer[out];
  out = (out + 1) % BUFFER_SIZE;
  count--;
  /* consume the item in next_consumed */
}

สาเหตุคือ count++ ในภาษาเครื่องไม่ได้เป็นคำสั่งเดียว แต่แตกออกเป็น 3 คำสั่ง (อ่าน, บวก, เขียนกลับ) ถ้า CPU สลับไปทำอีกฝั่งระหว่างกลาง ค่าที่เขียนกลับจะทับกัน

// count++
register1 = count
register1 = register1 + 1
count = register1
// count--
register2 = count
register2 = register2 - 1
count = register2

สลับลำดับคำสั่งเอง แล้วดูว่า count ออกมาเท่าไร

6.2 The Critical-Section Problem

โค้ดส่วนที่ห้ามเข้าพร้อมกัน

ระบบมี process P0 … Pn−1 แต่ละตัวมีโค้ดช่วงหนึ่งที่แตะข้อมูลร่วม เรียกว่า critical section กติกาคือไม่มีสอง process อยู่ใน critical section พร้อมกัน

โครงสร้างของแต่ละ process แบ่งเป็น 4 ส่วน

  • entry section ขออนุญาตเข้า (เหมือนเคาะประตูขอกุญแจ)
  • critical section ทำงานกับข้อมูลร่วม
  • exit section บอกว่าออกแล้ว (คืนกุญแจ)
  • remainder section โค้ดส่วนที่เหลือ

เงื่อนไข 3 ข้อของคำตอบที่ถูกต้อง

1. Mutual exclusion

ถ้า Pi อยู่ใน critical section แล้ว process อื่นต้องเข้าไม่ได้

ห้องน้ำมีกุญแจดอกเดียว ใช้ได้ทีละคน

2. Progress

ถ้าไม่มีใครอยู่ข้างใน แล้วมีคนอยากเข้า การตัดสินว่าใครได้เข้าต้องทำได้ ห้ามเลื่อนไปเรื่อย ๆ และให้เฉพาะคนที่ไม่ได้อยู่ใน remainder section มีส่วนตัดสิน

ห้องว่างแต่ไม่มีใครได้เข้า ถือว่าผิด

3. Bounded waiting

หลังจากขอเข้าแล้ว จำนวนครั้งที่คนอื่นแซงเข้าไปก่อนต้องมีขอบเขตจำกัด จึงไม่มีใครรอตลอดกาล (starvation)

ต่อคิวแล้วต้องได้เข้าสักวัน

ตัวอย่างใน kernel next_available_pid

ถ้า P0 และ P1 เรียก fork() พร้อมกัน ทั้งคู่อาจอ่านค่า next_available_pid = 2615 ไปพร้อมกัน ทำให้ลูกสองตัวได้ pid เดียวกัน ถ้าไม่มี mutual exclusion

Preemptive vs Nonpreemptive kernel

  • Preemptive แย่ง CPU จาก process ที่อยู่ใน kernel mode ได้ ตอบสนองเร็ว แต่ต้องออกแบบให้ข้อมูลใน kernel ไม่เกิด race condition
  • Nonpreemptive process ใน kernel mode จะรันจนออกจาก kernel, block หรือยอมคืน CPU เอง จึงไม่มี race บนข้อมูล kernel เพราะมี process เดียวอยู่ใน kernel ณ เวลาหนึ่ง
6.3 Peterson's Solution

คำตอบเชิงซอฟต์แวร์สำหรับ 2 process

int turn;          // ตาของใคร
boolean flag[2];  // ใครอยากเข้าบ้าง

while (true) {
  flag[i] = true;      // ฉันอยากเข้า
  turn = j;            // แต่ให้เธอก่อน
  while (flag[j] && turn == j)
    ;                   // รอ
    /* critical section */
  flag[i] = false;     // ออกแล้ว
    /* remainder section */
}

ใช้ตัวแปรร่วม 2 ตัว flag[i] บอกว่า Pi อยากเข้า และ turn บอกว่าตาของใคร

หลักคิดคือ “ฉันอยากเข้า แต่ให้เธอไปก่อน” ถ้าทั้งสองตั้ง turn เกือบพร้อมกัน ค่าที่เขียนทีหลังจะทับค่าแรก คนที่เขียนทีหลังจึงเป็นคนรอ

ข้อจำกัดบนสถาปัตยกรรมสมัยใหม่ CPU หรือคอมไพเลอร์อาจสลับลำดับ load/store จึงไม่รับประกันว่า Peterson จะถูกต้องเสมอ ที่ยังสอนกันเพราะเป็นตัวอย่างที่ดีว่าคำตอบต้องผ่านทั้ง mutual exclusion, progress และ bounded waiting
6.4 Mutex Locks

กุญแจดอกเดียว: acquire() แล้ว release()

acquire() {
  while (!available)
    ; /* busy wait */
  available = false;
}

release() {
  available = true;
}

while (true) {
  acquire lock
    critical section
  release lock
    remainder section
}

mutex ย่อจาก mutual exclusion มีตัวแปร boolean available บอกว่ากุญแจว่างไหม ก่อนเข้า critical section ต้อง acquire() พอออกต้อง release() ทั้งสองฟังก์ชันต้องเป็น atomic (ทำรวดเดียวไม่ถูกขัด)

ข้อเสียของแบบนี้คือ busy waiting process ที่รอจะวนลูปเช็กไปเรื่อย ๆ จึงเปลือง CPU ที่ process อื่นน่าจะได้ใช้ ล็อกแบบนี้เรียกว่า spinlock เพราะมัน “หมุน” รอ

ข้อดีของ spinlock คือไม่ต้อง context switch ระหว่างรอ จึงเหมาะกับระบบหลายคอร์ที่ถือล็อกกันไม่นาน

6.5 Semaphores

ตัวนับที่แตะได้ผ่าน wait() และ signal() เท่านั้น

wait(S) {
  while (S <= 0)
    ; // busy wait
  S--;
}

signal(S) {
  S++;
}

Semaphore S เป็นตัวแปรจำนวนเต็ม หลังกำหนดค่าเริ่มต้นแล้วจะแตะได้ผ่าน 2 operation เท่านั้น

  • wait() (บางตำราเรียก P) ขอใช้ ถ้า S ≤ 0 ต้องรอ แล้วลด S
  • signal() (V) คืน เพิ่ม S

ขณะที่ process หนึ่งแก้ค่า semaphore จะไม่มี process อื่นแก้ค่าเดียวกันได้พร้อมกัน

Counting semaphore

ค่าเป็นจำนวนเต็มใดก็ได้ ใช้คุมทรัพยากรที่มีหลายชิ้น เช่น เครื่องพิมพ์ 3 เครื่อง ให้ตั้ง S = 3 ใครจะใช้ก็ wait() (S ลดลง) ใช้เสร็จก็ signal() (S เพิ่ม) ถ้า S = 0 แปลว่าทรัพยากรถูกใช้หมด คนถัดไปต้องรอ

Binary semaphore

ค่าเป็นได้แค่ 0 หรือ 1 ทำงานคล้าย mutex lock ระบบที่ไม่มี mutex ใช้ binary semaphore แทนเพื่อทำ mutual exclusion ได้

Counting semaphore คุมเครื่องพิมพ์ 3 เครื่อง

6.6 Deadlock (ด้วย semaphore)

ต่างคนต่างรอกันและกัน

//  S = 1, Q = 1
//  P0              P1
wait(S);         wait(Q);
wait(Q);         wait(S);
  ...              ...
signal(S);       signal(Q);
signal(Q);       signal(S);

P0 ได้ S แล้วรอ Q ส่วน P1 ได้ Q แล้วรอ S ไม่มีใครได้ทำ signal() สักที จึงรอกันไม่มีที่สิ้นสุด

Deadlock คือสภาวะที่ทุก process ในกลุ่มรอเหตุการณ์ที่จะเกิดได้ก็ต่อเมื่อ process อื่นในกลุ่มเดียวกันเป็นคนทำให้เกิด รายละเอียดอยู่ในบทที่ 7

6.7 Priority Inversion

ตัวสำคัญที่สุดต้องรอตัวสำคัญน้อยกว่า

มี process 3 ตัว ลำดับความสำคัญ L < M < H โดย L ถือ semaphore S อยู่ แล้ว H ต้องการ S ด้วย H จึงต้องรอ L ซึ่งยังพอรับได้ แต่ถ้า M มาแย่ง CPU จาก L ได้ (เพราะ M > L) L จะปล่อย S ช้าลง และ H ก็ต้องรอนานขึ้นทั้งที่ M ไม่ได้ใช้ S เลย สรุปคือ M ที่ priority ต่ำกว่า H ไปทำให้ H ช้าลงโดยอ้อม ปัญหานี้เกิดได้เฉพาะในระบบที่มี priority มากกว่า 2 ระดับ

วิธีแก้คือ priority-inheritance protocol ให้ process ที่ถือทรัพยากรที่ตัว priority สูงรออยู่ ยืม priority สูงไปใช้ชั่วคราว พอคืนทรัพยากรแล้วจึงกลับไปเป็น priority เดิม

เปรียบเทียบไทม์ไลน์ มีและไม่มี priority inheritance

7.3 Necessary Conditions & Resource-Allocation Graph

Deadlock เกิดได้เมื่อ 4 เงื่อนไขเป็นจริงพร้อมกัน

1. Mutual exclusion

มีทรัพยากรอย่างน้อยหนึ่งชิ้นที่แชร์ไม่ได้ ใช้ได้ทีละ thread

2. Hold and wait

thread ถือทรัพยากรอยู่อย่างน้อยหนึ่งชิ้น แล้วรอขอชิ้นอื่นเพิ่ม

3. No preemption

แย่งทรัพยากรคืนไม่ได้ ต้องรอให้ thread ปล่อยเอง

4. Circular wait

รอกันเป็นวง T0 รอ T1, T1 รอ T2, …, Tn รอ T0

R1 ถูกจัดให้ T1, R2 ถูกจัดให้ T2 และต่างคนต่างขอของอีกฝ่าย เกิดวงจร T1 → R2 → T2 → R1 → T1

Resource-allocation graph ใช้วิเคราะห์ deadlock

  • วงกลม = thread, สี่เหลี่ยม = ประเภททรัพยากร, จุดในสี่เหลี่ยม = จำนวน instance
  • Request edge T → R หมายถึง thread กำลังขอ
  • Assignment edge R → T หมายถึงทรัพยากรถูกจัดให้ thread แล้ว

มีวงจร แต่ทรัพยากรมีหลาย instance แปลว่าอาจมีหรือไม่มีก็ได้

7.6 Deadlock Avoidance

อนุญาตเฉพาะคำขอที่ทำให้ระบบยัง “ปลอดภัย”

Avoidance ต้องรู้ล่วงหน้าว่าแต่ละ thread จะขอทรัพยากรมากที่สุดเท่าไร ทุกครั้งที่มีคำขอ ระบบจะลองคิดว่าถ้าให้ไปแล้วยังอยู่ใน safe state หรือไม่

Safe state คือสถานะที่มี safe sequence <T1, …, Tn> ที่ thread แต่ละตัวได้รับทรัพยากรที่ยังต้องการจาก (ทรัพยากรว่าง + ทรัพยากรที่ thread ก่อนหน้าคืนมา) จนทำงานเสร็จครบทุกตัว

ถ้าหา safe sequence ไม่ได้เลย สถานะนั้นคือ unsafe ซึ่งยังไม่ใช่ deadlock แต่มีโอกาสนำไปสู่ deadlock

ข้อเสียคือ แม้ทรัพยากรจะว่าง thread ก็อาจต้องรอถ้าการให้ทำให้ระบบ unsafe ทำให้ utilization ต่ำลง

deadlock เป็นส่วนหนึ่งของ unsafe ส่วน unsafe ไม่จำเป็นต้องเป็น deadlock

ชื่อมาจากธนาคารที่ต้องปล่อยกู้โดยไม่ให้เงินสดเหลือน้อยจนลูกค้าทุกรายถอนตามวงเงินสูงสุดไม่ได้ ใช้กับทรัพยากรที่มีหลาย instance มีโครงสร้างข้อมูล 4 ตัว (n = จำนวน thread, m = จำนวนประเภททรัพยากร)

จำนวนที่ว่างอยู่ของแต่ละประเภท

Max [n×m]

ความต้องการสูงสุดที่แต่ละ thread ประกาศไว้

Allocation [n×m]

จำนวนที่ thread ถืออยู่ตอนนี้

Need [n×m]

7.8 Recovery from Deadlock

ยุติ process / thread

  • Abort ทั้งหมดที่ติด deadlock แก้ได้แน่นอนแต่แพง เพราะงานที่คำนวณมานานต้องทิ้งแล้วทำใหม่
  • Abort ทีละตัวจนวงจรหาย overhead สูง เพราะต้องรัน detection ใหม่ทุกครั้งหลัง abort

Resource preemption

แย่งทรัพยากรจากบาง process ไปให้ตัวอื่นจนวงจรขาด ต้องตอบ 3 ประเด็น

  • Selecting a victim เลือกใครโดยให้ต้นทุนน้อยที่สุด
  • Rollback ย้อน process ที่ถูกแย่งกลับไปสถานะที่ปลอดภัย (หรือเริ่มใหม่ทั้งหมด)
  • Starvation ต้องไม่เลือกคนเดิมเป็น victim ซ้ำตลอด เช่นนับจำนวนครั้งที่ถูก rollback รวมเข้าไปในต้นทุน

8.1 Basic Hardware

แก้ด้วย (1) compaction ย้าย process ไปชิดด้านหนึ่งให้ที่ว่างรวมเป็นก้อนเดียว ทำได้เฉพาะเมื่อ relocation เป็นแบบ dynamic (execution time) และมีต้นทุนสูง หรือ (2) ยอมให้ process อยู่ไม่ต่อเนื่อง ซึ่งก็คือ paging

พื้นที่ที่จัดให้ใหญ่กว่าที่ขอ ส่วนเกินอยู่ในบล็อกที่ถูกจองแล้ว คนอื่นใช้ไม่ได้ เช่น ใน paging หน้าสุดท้ายของ process มักใช้ไม่เต็มหน้า

8.5 Paging

หั่นเป็นชิ้นขนาดเท่ากัน แล้ววางที่ไหนก็ได้

แบ่ง physical memory เป็นบล็อกขนาดคงที่เรียกว่า frame และแบ่ง logical memory เป็นบล็อกขนาดเท่ากันเรียกว่า page หน้าของ process จะไปลง frame ว่างตรงไหนก็ได้ ไม่ต้องต่อเนื่อง จึงไม่มี external fragmentation (แต่ยังมี internal ในหน้าสุดท้าย)

ที่อยู่จาก CPU แบ่งเป็นสองส่วน คือ page number (p) ใช้เป็น index ของ page table ของ process นั้น และ page offset (d) ระยะภายในหน้า

8.6 Structure of the Page Table

page table ใหญ่เกินไป ต้องจัดโครงสร้างใหม่

32-bit กับ page 4 KB ได้ 220 ≈ 1 ล้านช่อง ช่องละ 4 ไบต์ เท่ากับ 4 MB ต่อ process และต้องต่อเนื่องกัน จึงมี 3 วิธีลดขนาด

Hierarchical paging

page ตัว page table อีกชั้น (two-level) 32-bit กับ page 4 KB แบ่งเป็น p1 = 10, p2 = 10, d = 12 บิต p1 ชี้ outer page table, p2 ชี้ช่องใน page ของ page table

64-bit สองชั้นไม่พอ ในสไลด์จึงแบ่ง 3 ระดับ: 32 | 10 | 10 | 12

Hashed page table

นำ virtual page number เข้า hash function ได้ช่องในตาราง แต่ละช่องเป็น linked list ของ (page, frame, next) แล้วไล่หา page ที่ตรง เหมาะกับ address space ที่ใหญ่กว่า 32 บิต

Inverted page table

มีตารางเดียวทั้งระบบ หนึ่งช่องต่อหนึ่ง frame จริง เก็บ <pid, page> CPU ส่ง <pid, p, d> มา ระบบค้นหาว่าอยู่ช่องที่ i ได้ physical = <i, d> ประหยัด memory แต่ค้นช้า (ใช้ hash ช่วย) และทำ shared memory ได้ยาก

Standard swapping

ย้ายทั้ง process ออกไปเก็บที่ backing store (ดิสก์) แล้วนำกลับเข้ามาเมื่อจะรัน ทำให้ memory ที่ process ใช้รวมกันเกิน RAM ได้ แต่ย้ายทั้งก้อนใช้เวลามาก OS สมัยใหม่จึงไม่ค่อยใช้

Swapping with paging

ย้ายเฉพาะบางหน้า page out คือย้ายหน้าจาก memory ไปดิสก์ page in คือย้ายกลับ ใช้เวลาน้อยกว่ามาก Linux และ Windows ใช้แบบนี้ (และเป็นพื้นฐานของ virtual memory)

  • อธิบาย base/limit, เขียนเงื่อนไขเช็กที่อยู่ และรู้ว่าทำไมต้องโหลดด้วย privileged instruction

Error detection แค่รู้ว่าข้อมูลเพี้ยน เช่น บิตใน DRAM พลิก แพ็กเก็ตเพี้ยนระหว่างส่ง หรือบล็อกบนดิสก์เปลี่ยน เพื่อหยุดงาน แจ้งผู้ใช้ หรือเตือนว่าอุปกรณ์กำลังเสีย

  • Raw partition ไม่มีระบบไฟล์ ใช้ swap-space manager ที่เน้นความเร็วมากกว่าการประหยัดพื้นที่

  5. device controller สั่งอุปกรณ์ทำงาน เสร็จแล้วส่ง interrupt
  6. interrupt handler รับ interrupt เก็บข้อมูลลง buffer ของไดรเวอร์ แล้วปลุกไดรเวอร์
  7. device driver ดูว่างานไหนเสร็จ แจ้ง kernel I/O subsystem
  8. kernel ย้ายข้อมูลหรือ return code ไปที่ address space ของ process แล้วย้าย process ไป ready queue
  9. system call กลับ process ได้ข้อมูลแล้ว ทำงานต่อ

ระดับความเร็ว (latency) ของแต่ละอย่าง

ค่าประมาณตามภาพในสไลด์ (log scale) แต่ละขีดคือ 10 เท่า HDD ช้ากว่า DRAM ราวหนึ่งแสนเท่า

เช็กลิสต์ก่อนสอบ
  • รู้ส่วนประกอบ HDD (track, sector, cylinder, arm, head) และ seek time / rotational latency
  • อธิบายว่าทำไม NAND เขียนทับไม่ได้ และ FTL ทำหน้าที่อะไร รู้ว่า NVMe ต่อผ่าน PCIe
  • คำนวณระยะหัวอ่านของ FCFS (640), SCAN และ C-SCAN จากโจทย์ queue ในสไลด์ได้
  • แยก parity / checksum / CRC / ECC และ soft error กับ hard error
  • เรียงขั้น low-level format → partition → volume → logical format และรู้จัก MBR
  • เทียบ host-attached, NAS, cloud, SAN และ RAID 0/1/4/5/6 คำนวณ MTTDL ของ mirror ได้
  • อธิบาย memory-mapped I/O, polling vs interrupt, DMA และเส้นทาง read() ได้
  • แยก buffer, cache, spool และรู้ 3 เหตุผลของ buffering

12.2 Program Threats

process กับ kernel คือหนทางเดียวที่งานจะเกิดขึ้นบนเครื่อง เป้าหมายของผู้โจมตีจึงมักเป็นการทำให้โปรแกรมทำสิ่งที่ไม่ควรทำ หรือทิ้ง back door / RAT (Remote Access Tool) ไว้เข้ามาภายหลัง

Trojan horse

โปรแกรมที่ดูมีประโยชน์ แต่แอบทำสิ่งที่เป็นอันตรายด้วยสิทธิ์ของผู้ใช้ที่รันมัน

Spyware

แฝงมากับโปรแกรมอื่น แอบเก็บข้อมูลผู้ใช้ส่งออก หรือแสดงโฆษณา

Ransomware

เข้ารหัสข้อมูลของเหยื่อแล้วเรียกค่าไถ่เพื่อแลกกับคีย์

Trap door (back door)

ช่องลับที่ผู้เขียนโปรแกรมทิ้งไว้ ใช้ข้ามการตรวจสอบตัวตนได้

Logic bomb

โค้ดที่จะทำอันตรายเมื่อเงื่อนไขเป็นจริง เช่น ถึงวันที่กำหนด

Code review

การตรวจโค้ดโดยคนอื่นเป็นวิธีป้องกัน trap door และ logic bomb

Code injection: buffer overflow

#include <stdio.h>
#define BUFFER_SIZE 8

int main(int argc, char *argv[]) {
  int j = 0;
  char buffer[BUFFER_SIZE];
  int k = 0;
  if (argc < 2) return -1;
  strcpy(buffer, argv[1]); // ไม่เช็กความยาว!
  printf("K is %d, J is %d, buffer is %s\n",
         j, k, buffer);
  return 0;
}

Code injection คือการเพิ่มหรือแก้โค้ดที่จะถูกรัน มักเกิดจากการเขียนโปรแกรมไม่ปลอดภัยในภาษาระดับต่ำอย่าง C/C++ ที่เข้าถึง memory ผ่าน pointer ได้ตรง ๆ

strcpy() คัดลอกจนเจอ \0 โดยไม่สนขนาดปลายทาง ถ้า input ยาวเกิน 8 ไบต์ ส่วนเกินจะล้นไปทับข้อมูลที่อยู่ถัดไปบน stack

วิธีป้องกัน: ใช้ฟังก์ชันที่จำกัดความยาว (strncpy, snprintf), เช็กขอบเขต, stack canary, หน่วยความจำ stack ที่รันโค้ดไม่ได้ (NX bit) และ ASLR

พิมพ์ input แล้วดูว่าล้นไปทับอะไร

Denial of service

มี 2 ประเภท (1) ใช้ทรัพยากรของเครื่องจนไม่เหลือให้งานจริง เช่น applet ที่กิน CPU หรือเปิดหน้าต่างไม่หยุด (2) ทำให้เครือข่ายใช้การไม่ได้ ป้องกันได้ยากมาก เพราะใช้กลไกเดียวกับการใช้งานปกติ

Port scanning

ไม่ใช่การโจมตีโดยตรง แต่เป็นการสำรวจหาช่องโหว่ เครื่องมือจะลองเปิด TCP หรือส่ง UDP ไปยังพอร์ตต่าง ๆ เพื่อดูว่ามีบริการอะไร ผู้ดูแลระบบก็ใช้ตรวจระบบตัวเอง เช่น nmap ซึ่งเป็นโอเพนซอร์สสำหรับสำรวจเครือข่ายและ security auditing

12.4 User Authentication

รหัสผ่านเป็นวิธียืนยันตัวตนที่พบบ่อยที่สุด เข้าใจง่าย แต่ถูกเดา, หลุด, ถูกดักฟัง (sniff) หรือถูกส่งต่อให้คนอื่นได้ ส่วนใหญ่ใช้รหัสเดียวให้สิทธิ์ทั้งหมด เพราะต้องแลกกันระหว่างความปลอดภัยกับความสะดวก

วิธีเดารหัสที่พบบ่อย

  • ใช้ข้อมูลส่วนตัวของผู้ใช้ (ชื่อสัตว์เลี้ยง วันเกิด)
  • Shoulder surfing แอบมองข้ามไหล่
  • Human nature คนชอบตั้งรหัสง่าย จดไว้ หรือใช้ซ้ำ

Securing passwords UNIX ไม่เก็บรหัสตรง ๆ แต่เก็บ hash ซึ่งคำนวณง่ายแต่ย้อนกลับแทบไม่ได้ ระบบเองก็ถอดไม่ได้ ข้อเสียคือถ้าใครได้ไฟล์ไปก็ทำ dictionary attack ได้ (hash ทุกคำในพจนานุกรมแล้วเทียบ) จึงเติม salt (ค่าสุ่มต่อผู้ใช้) ให้รหัสเดียวกันได้ hash ต่างกัน

One-time password

ใช้รหัสครั้งเดียวทิ้ง (หรือ algorithm สร้างรหัส) ถ้าถูกดักฟังหรือแอบมองไป ก็ใช้ซ้ำไม่ได้ เป็นหนึ่งในไม่กี่วิธีที่กันปัญหารหัสหลุดได้

Two-factor

12.5 Implementing Security Defenses

Security policy

ขั้นแรกเสมอ บอกว่าจะปกป้องอะไร เช่น แอปที่เปิดสู่ภายนอกต้องผ่าน code review, ห้ามแชร์รหัส, สแกนพอร์ตทุก 6 เดือน เป็นแผนที่ไปสู่ความปลอดภัย ต้องให้คนรู้และทบทวนอยู่เสมอ (living document)

Vulnerability assessment

ตั้งแต่ social engineering, risk assessment (ประเมินมูลค่าทรัพย์สินกับโอกาสเกิดเหตุ) ถึง port scan แกนหลักคือ penetration test สแกนช่องโหว่ที่รู้จัก ตรวจ: รหัสสั้น/เดาง่าย, โปรแกรม privileged ที่ไม่ได้รับอนุญาต, โปรแกรมแปลกในไดเรกทอรีระบบ, สิทธิ์ไฟล์ระบบผิด, search path อันตราย (เช่น current dir, /tmp), โปรแกรมระบบถูกแก้ (ดูจาก checksum), daemon ที่ซ่อนอยู่

Intrusion prevention

ตรวจจับการบุกรุกแล้วตอบสนอง ต่างกันใน 3 แกน

  • เวลา ตรวจแบบ real time หรือหลังเกิดเหตุ
  • input คำสั่ง shell, system call, header/เนื้อหาแพ็กเก็ต
  • การตอบสนอง แจ้งเตือน, kill process หรือเบี่ยงผู้บุกรุกไปที่ honeypot (ทรัพยากรปลอมที่ดูเหมือนจริง ไว้เฝ้าดูพฤติกรรม)

Virus protection

antivirus ค้นหารูปแบบคำสั่ง (signature) ของไวรัสที่รู้จักแล้วลบออก มีแคตตาล็อกนับพัน แต่ป้องกันดีที่สุดคือ safe computing ซื้อซอฟต์แวร์ที่ยังไม่แกะ หลีกเลี่ยงของเถื่อนหรือของฟรีจากแหล่งที่ไม่รู้จัก

Auditing, accounting, logging

ทำให้ระบบช้าลงบ้าง แต่มีประโยชน์ log การ authentication/authorization ที่ล้มเหลวบอกความพยายามบุกรุกได้ accounting ช่วยจับความผิดปกติของประสิทธิภาพ เช่น Cliff Stoll จับผู้บุกรุก UNIX ได้จากความผิดปกติใน accounting log

Firewall

คอมพิวเตอร์ อุปกรณ์ process หรือ router ที่คั่นระหว่างฝั่งที่เชื่อถือได้กับไม่ได้ จำกัดการเชื่อมต่อตาม address ต้นทาง/ปลายทาง พอร์ต และทิศทาง พร้อมบันทึก log แบ่งเครือข่ายเป็นหลายโดเมนได้
